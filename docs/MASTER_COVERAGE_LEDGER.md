## Reading the ledger

Evidence is classified strictly:

- `implemented-live`: exercised through the current StatePort service, not a
  mocked network.
- `implemented-not-live-validated`: executable code exists and has focused
  unit, contract, service, or component evidence, but the current integrated
  browser path has not been accepted.
- `frontend-only`: production frontend exists without a production backend
  contract.
- `mock-only`: Scenario Lab/demo behavior only.
- `partial`: some required authority, backend, frontend, or evidence is absent.
- `superseded-by-better-current-design`: the current design passes the
  functional-equivalence gate and has inspectable evidence.
- `planned`: sequenced current or future work with enough authority to plan.
- `deferred`: blocked by an exact external dependency, unresolved product
  semantics, or disproportionate scope.
- `rejected`: conflicts with Stateware invariants or lacks sufficient value.

“Validated” below means the stated validation only. It never implies remote
acceptance, human acceptance, release, or superiority.

Each requirement row deliberately combines related fields to keep this ledger
reviewable: the first description column records source, intended outcome, and
non-negotiable invariant; the implementation column records backend contract
and frontend surface; the final three columns record status/evidence, the exact
gap/priority/dependency, and acceptance/rollback/first next action. A status is
never inferred from a similarly named component.
