# Failure Scan — SP-001b Local Runner

## What happens if the instance references a template that does not validate?

`run_instance` calls `template_validator.validate_instance` defensively after
performing its own load and schema-file checks. If the referenced template fails
validation, the issues are formatted as `"<path>: <message>"` strings and
returned in `RunResult.errors`. The CLI prints them as JSON and exits non-zero.
The runner never reports success for an invalid instance.

## What happens if `instance/state/` is missing required schema files at run time?

After the template is loaded, the runner iterates over `template.spec.schemas`
and checks that each path resolves to a file under the instance directory.
Missing files produce `missing required state file: <path>` errors, exit 1, and
a JSON result with `errors` populated.

## What happens if the instance `status` is not `active`?

The runner does not treat a non-active status as an error. It echoes the status
value in the `status` field, adds a log entry noting the status, and exits 0.
Enforcement of status-based behaviour belongs to future slices (quota,
approval, audit).

## What adjacent failures are likely when SP-002 (Telegram adapter) calls the runner?

- The adapter may pass an instance path that does not exist or is not readable.
  The runner returns a parse/read error and exit 1.
- The adapter may rely on the output shape. If SP-002 needs structured events,
  the current human-string `logs` array will need to be supplemented or
  replaced with a machine-events array.
- The adapter may invoke the runner concurrently. SP-001b keeps no global
  mutable runner state, but file-system races on instance/state/ are possible
  and are out of scope for this slice.

## Anti-brittleness notes

- Template reference resolution reuses `template_validator.checks.check_template_ref_resolves`;
  the runner has no private relative-path rule.
- State file checks derive the expected list from `template.spec.schemas`, not
  a hard-coded demo list.
- Output is deterministic: no timestamps, random IDs, or environment strings.
- The runner mutates no instance files.
- All file-loading and model-construction errors are caught and surfaced as
  structured `RunResult.errors` instead of raising exceptions.

## Execution model

SP-001b is not a state machine. It is a deterministic script that loads state
metadata, verifies expected files exist, and prints a structured result. A
state-machine-backed execution model is a future slice concern.

## How the runner fails loudly and traceably

- Every failure path returns a non-zero exit code and a JSON `errors` array.
- Errors include the file or path involved (`instance.yaml`, `template.yaml`,
  `state/<file>.yaml`, or validator issue paths).
- Logs show how far the runner progressed before the failure.

## Residual risk

- The runner is local-only; there is no quota enforcement, approval gate, or
  persistent audit log beyond the execution result.
